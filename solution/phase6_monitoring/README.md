# Phase 6 - Monitoring, Drift Detection & Governance

Turns the Phase 5 prediction log into a monitored, governed signal: a request
validation gate, a drift job (feature / prediction / performance drift), an
append-only `drift_report` + audit trail, a scheduler sidecar, a Grafana
dashboard, and the governance documents.

## Run

```bash
docker compose up -d          # starts + bootstraps Postgres (../docker-compose.yml)
uv run python phase6_monitoring/run_phase6.py     # DDL + notebook + drift runs + tests
```

`run_phase6.py` regenerates and executes **`phase6.ipynb`** (the deliverable),
which seeds two comparable traffic windows into `prediction_log`, runs the drift
job for both models on each, writes `capstone_solution.drift_report`, and
produces the charts, CSVs and `PHASE6_FINDINGS.md`. It then runs the pytest
suite.

```bash
uv run pytest phase6_monitoring/tests -q                 # drift maths + gate + DB end-to-end
uv run python -m phase6_monitoring drift-job --window drift   # one drift pass
uv run python -m phase6_monitoring seed                       # re-seed the demo windows
uv run python -m phase6_monitoring gate --window drift        # validation-gate report
```

## The monitoring stack

```bash
docker compose -f phase6_monitoring/docker-compose.yml up --build
```

| Service | Port | Role |
|---|---|---|
| `postgres` | 5433 | the analytics DB + prediction / drift logs |
| `api` | 8000 | the Phase 5 prediction service (`/docs`) |
| `scheduler` | - | seeds the demo windows, then runs the drift job every `DRIFT_INTERVAL_SECONDS` (120 s here) |
| `grafana` | 3000 | the **Hospital Drift** dashboard (anonymous viewer) |

The Grafana dashboard reads `drift_report` and `prediction_log` directly:
feature PSI over runs (with the 0.10 / 0.25 lines), prediction-mix PSI, Model B
recall on Rejected vs the Phase 4 baseline, the validation-gate fail rate, the
active-alert table, and served volume by predicted class.

## What is measured

| Signal | Method | Reference |
|---|---|---|
| Request validity | Phase 2 rule registry (`capstone.data_quality`) as a batch gate | fixed enum domains + pre-submission numeric ranges |
| Feature drift | PSI (deciles) + two-sample KS per monitored feature | Phase 3 **test** window |
| Prediction drift | predicted-class-mix PSI | Phase 3 test-window predicted mix |
| Performance drift | recall on the costly class + net recovered, actuals joined on `visit_id` | Phase 4 operating baseline |

Alert rules live in one place - `capstone.monitoring.ALERT_RULES` - and are
cited by `governance.md`. Model A monitors only its own manifest feature list,
so it is never compared on a billing distribution (the leakage register, still
enforced at monitoring time).

## Layout

```
notebook.py -> phase6.ipynb    the deliverable (regenerated by run_phase6.py)
run_phase6.py                  entrypoint: DDL + notebook + tests
seed_traffic.py                replay Phase 3 test-window visits -> prediction_log (baseline + drifted)
drift_job.py                   one scheduled drift pass -> drift_report
scheduler.py                   the compose sidecar loop
__main__.py                    `python -m phase6_monitoring {drift-job|seed|gate|scheduler}`
make_charts.py  report.py      house-style charts + PHASE6_FINDINGS.md
sql/drift_report.sql           drift_report, prediction_override, v_prediction_audit, append-only trigger
grafana/                       datasource + dashboard provisioning
governance.md  retraining_policy.md  runbook.md
tests/                         PSI/KS, gate, feature drift, end-to-end drift job, governance SQL
Dockerfile  docker-compose.yml
```

Reusable logic is in `src/capstone/monitoring.py`.
